The Olympic plant room (`plant_pool_02`) is not in `SCHEMATICS`; its network comes from `olympicPlumbing()` (`src/toolkit/gallery/logic/olympic-plumbing.ts`), with the annex `olympic-annex.ts`. `roomNetwork(room)` in `src/toolkit/gallery/logic/world-in-model.ts` returns the enhanced network for every built room, Olympic included, and is what 129 reads.

## 2. The graph: nodes, identity, ports, edges

### Node identity

One id scheme, consistent with 129's rows, 125's refs and `blocks.ts` paths: **`<room>/<sort>:<id>`**, where `<sort>` is 129's (`node`, `fitting`, `link`) or one of three new sorts (`part`, `alarm`, `state`). Only active nodes (section 2a) have pages; a `link:` id and a passive fitting's `fitting:` id are identities, not pages (see "Where connector refs go" below).

- `plant_pool_03/node:cabinet`, `plant_pool_03/fitting:jacuzzi.isolator`, `switch_room/node:incoming` — schematic and enhanced-network items, exactly 129's model refs prefixed by their room, so a 129 row's `model` and `room` give its page with no lookup.
- `plant_pool_03/part:cabinet/pump` — a part inside a node whose state the world keeps but the schematic does not draw (the cabinet's circulation pump, `jacuzziPumpCalled`; a boiler inside the boiler house's node). Parts come from the kinds' part manifests where they exist (`IDENTIFIED_KINDS` in `identification.ts`, `BlockKind.parts`) and otherwise from the state adapter (section 4.3); the path after `part:` uses `blocks.ts`'s `/`.
- `<room>/alarm:<AlarmId>` — an annunciator window (`control_room/alarm:mains-fail`) or a location board's point (`<location room>/alarm:<id>`), a part of its annunciator; its state is `annunciator.windows[id]` (or the location board's), its sources `ALARM_SOURCES` (section 3, join 8).
- `world/state:<slice>[/<key>]` — leaf world state outside the four domains, from `World`'s own fields: `world/state:controlRoomMode`, `world/state:lifts/<id>`, `world/state:lighting/<zone>`.

An object with no model at all (a plant door, a sign) has no graph id: it is an architectural object (section 2a) with an architectural object page, not a node.

Graph ids are not `blocks.ts` addresses: `parseAddress` splits on the first `:` and would read `part:cabinet/pump` as a field, so the graph has its own parser (`parseNodeId`: room, sort, id) and keeps graph ids and world addresses apart; where a node's state does live in a `Block` (`identifiedPlant`), its adapter holds the `blocks.ts` address separately. The page is per node, not per field. The URL carries the id percent-encoded.

### Where connector refs go

Pipes and cables are bound today as `link:` refs (`Binding` in `world-in-model.ts`), and passive fittings as `fitting:` refs, but connectors have no page (2a). So every connector ref resolves to a **connector run**: the maximal sequence of passive pieces between two active nodes (or an active node and a boundary), from 129's `alongOf` (which also places fittings the plumber's `along` omits). A run's id is `run:<room>/<first link id>/<index>`, derived (`index` its place along that link, from 0). One link can hold several runs, because an active fitting splits it (the Jacuzzi's "Drain to waste" link has the active `jacuzzi.drain` valve in it, so a run on each side), and one run can span several links. So `resolveRef(room, ref) → ResolvedTarget[]` returns every target, in order along the link, each `{ page: NodeId, anchor?: string, label: string }`:

- an active node's or active fitting's ref → its own page;
- a passive fitting's ref → its one run; a `link:` ref → every run the link holds, in order (one for most links; two or more where an active fitting splits it), each resolved to the page of the run's upstream active end (by the link's port orientation; the end with the source port), at the anchor `#run-<run id>`, the collapsed edge's section in that page's "How does it connect", which lists the run's pieces in order, its medium and its far end; the downstream end's page has the same section under the same anchor;
- a run ending at a boundary with no active node on this side (only a boundary) → the far active end's page.

Where several targets come back, the caller lists them all ("Drain to waste: run 0 → drain valve; run 1 → waste"), never picking one. This is where 129's model-node column, 130's links in (section 7), 4.2's neighbours and 4.6a's object rows send a connector ref; no link target is ever a connector's own page. Tested on the Jacuzzi's "Drain to waste" link (two runs) and on a link with no active fitting (one run).

### Ports and edges, per domain

Ports are the schematic's: each `PlumbEdge` names a `sourcePort` and `targetPort`, and the plumber's fittings split a link into the sequence `node → fitting … → node` (`along`). A node's ports are the distinct `(port, medium, direction)` of the links at it; a fitting has `in` and `out` (`FITTING_PORTS`). Edges are the link segments between neighbours in that sequence, the same walk as 129's `connectionsOf` (using its `alongOf`, not the plumber's `along` alone).

**Every `GraphEdge` carries, mandatorily: `kind`, `direction` and `via`** (provenance: a file and symbol, or the declared table entry and its probe test). Edge kinds are kept apart (second opinion): `connects` (a schematic segment between active nodes, its run collapsed; its direction is the link's port orientation, not proof of an effect in every operating state), `contains` (a part to its parent node's port, from a declared part-port table, section 9 example 2), `feeds` (a cross-room supply join, section 3) and `raises` (an alarm node from each of its `ALARM_SOURCES`). All four join two `NodeId`s.

**Controls, readings and copies are typed relations, not `GraphEdge`s,** because their one end is a world object's control or reading (131's `Control` and `Reading`, identified by their descriptor's `ref` and their `key`), not a graph node: `ControlRelation { control: { room; ref; key }; target: NodeId | 'unresolved'; via }` (from `Control.targets` through `resolveRef`, or a tag through the derived tag index; a target neither resolves is `unresolved`, shown as such), `ReadingRelation { reading: { room; ref; key }; target: NodeId | 'unknown'; via }` (from the offered `Reading.reads`, else `PART_BINDINGS`, else `unknown`), and `CopyRelation { board: ref; copy: ref; via }` (129's `boardCopies`). `relationsOf(graph, nodeId)` returns them for a node's sections 4.5 and 4.6; the later impact search may follow them into a node, but they are kept out of `neighbours`. Topology is not causation: a node touching power, water and heat links is not taken to mean every input affects every output; only a probed driver (section 4.4) asserts that. The later impact search must choose which kinds it walks. Medium is the link's `medium`, mapped to the brief's words: `water` → water; `heat` → heat; `power` → power; `chemical` → chemical; `gas`, `air`, `oil`, `flue` kept as their own; `control` → signal. **alarm** has no medium in the schematics; alarm edges are the derived edges of section 3.

- **Electrical.** The switch room's schematic (`switch-room-schematic.ts`: `incoming` → `main-switch` → `changeover` → `switchboard` → `rooms`, `lighting-board`, `central-battery`, `generator-cable` as boundary) and each room's own electrics (`roomElectrics` in `schematic-parts.ts`: `busbar` → `switch-fuse` → each machine's `power` port, with the plumber's `power-isolator` fittings). The world's state: `plant.sources.power`, `plant.changeover` (`changeover.ts`, `switchboardLive`), `plant.feeders[room]` (one per `ServiceRoom`, asset and tag in `ROOM_SWITCH_FUSES`, `installed-feeders.ts`), `plant.isolators[name]` (`ISOLATORS`), `lighting` (`lighting.ts`), `centralBattery`, and the starters in `motors` (`MOTORS`, each with its isolator).
- **Heating.** The boiler house schematic (`boiler-house-schematic.ts`) for boilers, pumps, headers and valves; state in `boilerHouse` (`BOILER_TAGS`, `stepBoilerHouse`), its sequencer (`stepBoilerSequencer`, `SEQUENCER_ALARMS`), `boilerGas` and `gas`, and the ring `lthw` (`stepRing`, `ringDraw`, consumers by `consumerK`). Each plant room's `heating` node (`heating-main`) with its `heating-flow` / `heating-return` links is where heat enters the room's graph.
- **Hydrodynamic.** Every room's water links and their fittings; the Olympic network from `olympicPlumbing()`; state in `installedValves`, `loungeValvePositions`, `olympic`, `olympicTank`, `pools`, `jacuzzi`, `spaFilters`, `loungeFilters`, `wetHall`, `motors`.
- **Chemical.** The `chemical` links (day tanks from `dayTanks` in `schematic-parts.ts`, the hypo and acid stores in `back-room-schematics.ts`, the CO₂ schematic `co2-schematic.ts`, the Olympic chemical schematic `olympic-chemical-schematic.ts`, the Aqualis schematic `aqualis-schematic.ts`); state in `chemicals`, `distribution` (`keptBy: 'distribution'` valves), `dosingPumps`, `aqualis`, `treatment` (the water's chemistry), `chemControl`; the air's chemistry in `airHandling` and `gas` zones.
- **Control and warning.** `control` links in the schematics (mimics, valve panels, control plates); 131's `Control.targets` (a control → what it works); the annunciators (section 3); controllers and interlocks that are code, not schematic (sequencer, Wash-O-Tron, Aqualis, cabinet boot), present as part nodes with derived edges (section 3).

Rooms with no schematic (the Olympic plant room's chemical side aside, any room `roomNetwork` returns nothing for) are listed as "no model network" in the Simulation catalogue, not invented.

## 2a. What gets a page: tiers and groups (the owner, 2026-11-02)

Not everything in the simulation matters equally. Each graph kind declares its tier once per kind, never per object, in a new exhaustive table `sim-graph/tiers.ts`: `graphTier(sort, kind) → 'active' | 'connector' | 'group-one' | 'group-many' | 'unknown'`, keyed by schematic node kind (`incoming-supply`, `room-feeders`, `boiler-cascade`, …), `FittingKind`, and the `link`, `part`, `alarm` and `state` sorts. It is separate from `object-class.ts`, which classifies catalogue object kinds and does not know schematic kinds such as `incoming-supply` or `room-feeders`; architectural objects are recognised by their look-audit record's class (127's `TargetRecord.class === 'architectural'`, which a plant door gets from its scene mark, since `object-class.ts`'s `ARCHITECTURAL_KINDS` does not list doors), because they are world objects outside the graph. A test walks every node and fitting kind in `SCHEMATICS` and the Olympic network and lists those `graphTier` returns `unknown` for; an unknown kind is shown as `unknown` on its page and in the list (not a flag, not guessed), and a node of unknown tier is given a page, so nothing is hidden:

- **Active nodes** hold or change state: machines, valves, pools and tanks, sensors, controllers, alarms and annunciators, feeders and isolators. Only they get node pages, and "what connects to what" is asked between them.
- **Passive connectors** simulate nothing and only carry a signal from one active node to the next: pipes, cables, conduits, plain busbars, and passive fittings (bends, tees, reducers). They are justified by the model (every pipe is one of a schematic's connections) but not simulated. A run of them collapses into one edge between two active nodes, carrying its medium and the list of pieces it passes through (each linking to its 129 audit row where drawn); a "show connectors" switch expands an edge back into its pieces. They get no page and none of the active-node flags; their one check is the one that justifies them: every connector run joins at least two active nodes, or an active node and a room boundary, and a run that connects nothing is flagged as unjustified dressing.
- **Architectural objects** (doors, signs, electrical and fire fittings) are outside the graph: they get an architectural object page, linked from the catalogue, saying they are not simulated (the owner chose this for doors, 2026-11-02). Its route is `bench.html?bench=sim-object&room=<room>&ref=<125's ref>` (encoded); it shows the object's name, kind, class (`architectural`, from its 127 record), room, a link to its row in its room's audit (129, `#row-<ref>`) and to its look, and "not simulated: no node, no edges". The control room doors are the exception: their page also lists the leaf `world/state:controlRoomMode` that decides where they lead.
- **Groups**, of two kinds, declared by the kind, not guessed:
  - **Simulated as one, drawn as many** (a ganged CO₂ cylinder bank): one node; its page says "simulated as one, drawn as N objects" and lists them, each linking to its object's audit row; each member object's audit row says it is part of the group and not simulated individually, and is never flagged unbound. Where the model knows the member count, a drawn count that differs is flagged.
  - **A group of individually simulated members** (the boiler house: three cascades, `cascade-1` to `cascade-3` in `boiler-house-schematic.ts`, each of two boilers, B-501 to B-506, each boiler with its own state in `boilerHouse`, all sequenced by the CM6 cascade manager): blocks within blocks. Each cascade has a page of its own (its two boilers listed, linking up to the cascade manager that sequences it), each boiler has its own page linking up to its cascade, and edges can be followed at either level.

## 2b. Location (the owner, 2026-11-02)

A node is abstract and has no place of its own, but location is one of the most useful ways to tag and filter the graph ("every node that connects to objects in the boiler house"). So every node carries locations derived from the data, never written by hand, in three kinds:

- **Home room:** the room whose schematic or network defines it (a Jacuzzi valve's is `plant_pool_03`; the switch room's feeders' is the switch room); none for world-wide state (the weather, the LTHW ring as a whole, which spans rooms, lists the rooms it passes through instead).
- **Shown in:** every room holding an object bound to it or a display, lamp or mimic showing it (a Jacuzzi alarm is shown in `plant_pool_03`, the old control room and the bridge).
- **Touches:** the rooms of its direct neighbours' bound objects (one step only; the exhaustive version belongs to the later impact search).

**Coverage.** "Shown in" and "touches" depend on what is described, so each room carries a coverage status, `RoomCoverage = { descriptors: 'described' | 'not described'; scene: 'scanned' | 'not scanned'; network: 'model' | 'no model network' }` (descriptors from 131's `DESCRIBED_ROOMS`; scene from whether 127's scanner has been run for it this session). A node's "shown in" is a list plus the rooms whose coverage is incomplete, shown as "unknown in: …"; absence of a representation in an uncovered room is unknown, never false.

For a portable object, its default location (where the game places it at the start) and, where the world holds it, its current one are given separately.

The `?dev` Simulation list and the pages filter by room on any of the three (home, shown in, touches), and by domain, tier and flag, so "every active node that touches the boiler house" is one filter. A room's audit (129) gains a link to that filtered list for its room.

**Later, not in this mission (the owner, 2026-11-02):** connectors will get pages of their own in a separate edges report (the owner calls it a vertices report), the counterpart of this nodes report: a page per pipe, cable or conduit run, plain as it will be. It is less useful for auditing, so it waits; until then a connector ref resolves to its run's anchored section on the active node's page, as above.

## 3. How the domains join (found, not invented)

Only joins the code already states are edges. Each is a pure function returning `GraphEdge`s with `via` naming its evidence (a file and symbol), so the page can show why the edge exists.

1. **Same node, several media (in-room).** A schematic node with links of more than one medium is where domains meet: the Jacuzzi cabinet has `power` (from the switch-fuse), `water` and `heat` (`heating-flow`) ports. The page shows the ports side by side; that power drives the water is asserted only by the cabinet's probed drivers (`jacuzziPumpCalled` reads supply), never inferred from the ports.
2. **Room supply to switch room (power, cross-room).** The switch room's schematic has one aggregate `rooms` node (kind `room-feeders`), but the world keeps one feeder per service room (`plant.feeders[room]`). So the graph gives `rooms` one part per service room, `switch_room/part:rooms/<ServiceRoom>` (e.g. `switch_room/part:rooms/plant_pool_03`), each with state `plant.feeders[room]` and tag and asset from `ROOM_SWITCH_FUSES` (which `satisfies Record<ServiceRoom, …>`, so every service room has one). The aggregate `rooms` node reaches its parts by `contains` edges, `switch_room/node:rooms` (port `null`) → each `switch_room/part:rooms/<ServiceRoom>` (port `null`), direction forward, `via` `ROOM_SWITCH_FUSES` and `PlantServices.feeders`, so the schematic's `switchboard` → `rooms` link carries on to every feeder. Each room's `switch-fuse` node is joined to its own feeder part, not to the aggregate, keyed by room through `ROOM_SWITCH_FUSES` and `ROOM_SERVICES`; `serviceAvailable` (`services.ts`) is the evidence that the room's feeder and the switchboard gate it. `UTILITY_SOURCE` names a source room, not a port, so each cross-room join is an explicit mapping table (room node ↔ source node and port), tested, never a join by room name alone.
3. **Heating main to boiler house (heat, cross-room).** A room's `heating-main` node joins the LTHW ring's consumers. These are keyed by use, not by room (`heat-consumers.ts`: `pool_XX/water`, `pool_XX/air`, area ids), so a room's heating main may map to several consumers; the mapping is an explicit table.
4. **Water service, waste and boundary nodes (water, cross-room).** A `water-service` node joins the wet hall's (`UTILITY_SOURCE.water`); the corridor water schematic's `boundary` nodes name their other ends (`wet-hall-boost`, `wet-hall-pit`, each room's `-make-up` and `-waste`); a room's `boundary` node is joined to the corridor's node of the same name. Where a boundary's other end cannot be found from the code, it stays a dangling boundary and the page says so (no guessing).
5. **Chemical supply (chemical, cross-room).** Day tanks' fill links join the distribution selectors (`chemical-distribution.ts`, `DAY_TANKS`) and the stores (`UTILITY_SOURCE.chemical = 'hypo_store'`; `serviceAvailable` also needs the acid store's feeder, a second upstream the table must carry).
6. **Control → model (signal).** 131's `Control.targets`: a control on object A that targets `fitting:x` or a tag is a `ControlRelation` (section 2) from A's control to that node, not a `GraphEdge`; its room is the descriptor's room. This is 129's `controlledBy` / `controlsOf`, reused.
7. **Board copies (signal).** 129's `boardCopies()`: a plant room mimic and its control-room copy share one world state, a `CopyRelation` both ways, not a `GraphEdge`.
8. **Model → alarm (alarm).** Each annunciator window's condition is code in `plantReadingOf(...).alarms` and each location board's in `LOCATION_ANNUNCIATORS`. A new declared table, `ALARM_SOURCES: Record<AlarmId, NodeId[]>` (beside the alarms, in `logic/`), names the nodes each window reads; it is checked, not trusted. A fresh world's windows are dark until `stepWorld` senses them, so each probe changes one listed source at a time, steps the world, and asserts both the condition in `plantReadingOf(...).alarms` and the window going to `flashing`; a compound condition (`flow-low`, `dosing-inhibit`) takes a probe per source. Alarm → annunciator: every `AlarmId` reaches the one `AnnunciatorState`, and through it the old control room's board and the bridge's displays (found from the components that read `world.annunciator`, listed once in the same module).
9. **World state reading the plant (leaves).** A leaf is joined only where the code reads plant state into it (the lighting's ways from the switchboard, `lightingWaysLive`; the control room doors from `controlRoomMode`); a plant door has no join.

Joins that are only implicit in step functions (the boiler's firing reading ring flow; dosing inhibited by circulation) are not edges until a declared table names them and a probe test proves them, as for alarms. The first delivery declares only those the four example nodes need.

## 4. The seven sections

Every section is a pure function `(graph, nodeId, inputs) → SectionData`, rendered by one view. A blank is a finding, not an error (129's rule).

### 4.1 What is it

Path (the node id, and its `blocks.ts`-style address where the node has one), domain (from its media; several if it joins domains), kind (the schematic node's `kind`, the fitting's `FittingKind`, `link`, or the part's kind), room (`ROOMS` name), tag (the schematic code with the room's code, `PL3-CAB1`, or the fitting's tag from `MODEL_VALVES` / `INSTALLED_VALVES`; never written by hand), derived name and description (`componentDescription` / `describeComponent` in `equipment-catalogue.ts` and `component-descriptions.ts`, as the inspection overlay has it), and the bound object's maker (`brands.ts` by kind, as 129's `makerOf`).

### 4.2 How does it connect

Its ports, each with direction (source port = out, target port = in; a fitting `in`/`out`), medium, and the active node on the far side, each a link to that node's page; between them, the collapsed connector run as its own anchored section (`#run-<run id>`, see section 2), its pieces listed in order (each with its 129 row link where drawn) and expanded inline by the "show connectors" switch; 129's `drawn` / `model only` / `boundary` label where the node is in a built room. Cross-room joins from section 3 appear as the far side of the boundary.

### 4.3 What state does it hold

From a **state adapter** per node kind: `StateAdapter = { fields(node) → FieldSpec[] ; read(world, node) → Record<string, unknown> }`, where `FieldSpec` is name, type, unit, range or values, saved (whether it lives in `World`, so in `save.ts`), and normal (from the schematic: a fitting's `normally`, an identified part's `normal`). Adapters are built from what already says where state lives: `statusBindingFor` (pumps, tanks, cabinets, UV, valves), `keptBy` on fittings (`identified` → `identifiedPlant` via `read`; `register` → `installedValves`; `distribution` → `distribution`), `ROOM_SWITCH_FUSES` (feeder → `plant.feeders[room]`), `ISOLATORS`, `MOTORS`. Values and ranges from the types where they are unions (`StarterMode`, `AlarmWindow`, `ChangeoverPosition`) and from 131's `Control.inputs` and `Reading` where the type is open. The current value is read from `newWorld()`; a node with no adapter shows "state not found in the world", which is section 7's input. Never default missing state to Off (`doc/equipment-status.md`).

### 4.4 What makes it change

Per adapter, declared and probed like section 3's alarm table (a test changes the driver and steps, and asserts the state moves): its drivers (its inputs through its ports, the step function that changes it, its controller, the controls whose actions set it from 131's `targets` and `action`), whether instant (an action) or over time (a step), the faults and trips it models (only those its state has, by the status-words rule: On/Off unless faults are modelled), and the event-log lines it can produce (which of `EVENT_SOURCES` notices it; a sample line made by running that source over a preset world before and after). A node's own lines are told apart from a related object's: the cabinet pump's trip is logged by `watcherEvents` (`watchers.ts`), not by `pumpEvents`, which watches the motor starters and the wet-hall booster.

### 4.5 What is it related to

Direct neighbours only: upstream (edges into it), downstream (edges out of it), controls acting on it (section 3, join 6), sensors and readings reading it (131's `Reading` has only `read(world)`, no model target, so this needs a new optional `Reading.reads: string[]` of model refs, proposed to 131's owner, filled for the example nodes; mimic lamps through board copies), alarms it can raise (the inverse of `ALARM_SOURCES`) and on which annunciators (the old control room's board, the bridge, any location board).

### 4.6 Where does it appear in the world

Bound objects: 127's scene marks and the room's `world-in-model` binding (`{ node }`, `{ fitting }`, `{ link }`). A node may have many representations in the world (the owner, 2026-11-02): a fault code shown on several annunciators, because codes are shared between them or because an annunciator is duplicated (a plant room's board and its control-room copies, 129's copies). Every one is listed, grouped by room, each saying why it is there (bound directly, a shared code, a copy of another board), and each linking to that object's own audit (its row in its room's audit, 129, from which its look link and its kind's item audit are reached), not to a look link directly; displays, lamps and mimics showing it here and in both control rooms (board copies, readings); whether the player can see it (any bound object or reading) and act on it (any control targeting it). Where a room's coverage (2b) is incomplete, its representations are "unknown", not absent. From data only; a binding known only from a scene is fetched by 127's scanner for that one room on demand (a button, not on load).

### 4.6a The reverse: from an object to its nodes (the owner, 2026-11-02)

Every object's audit (its row in its room's audit, 129, and each placement on its kind's item audit, 130) shows the simulation nodes bound to it, each a link through `resolveRef` (section 2). An object binds at most one node at its own level (a valve to its fitting, a pump to its block, an annunciator to its own power and fault-relay node), and its ports line up with that node's ports, listed beside them. Composite objects bind more through their named parts, each part to its own node (a mimic board's lamps and readouts to the alarm and reading nodes they show; the Jacuzzi cabinet's pump part to `part:cabinet/pump`), listed under the part. Architectural objects say they are not simulated; members of a group say which group node they belong to (2a).

**The data contract.** Today 127's `TargetRecord` has one object-level `model` ref and `parts: string[]` (labels only); 129's `AuditRow` has the same one `model`; 131's `Reading` has no model ref. Nothing yet maps a part or a port to a node, so this mission declares that mapping itself and offers the fields to their owners:

- **Owned by 138:** `sim-graph/part-bindings.ts`, `PART_BINDINGS: Record<kind, Record<partLabel, PartBinding>>`, keyed by the object's kind and 127's part label, where `PartBinding = { node: string /* a graph id template, room-relative: 'part:cabinet/pump', 'alarm:mains-fail' */; ports?: Record<objectPort, nodePort>; each?: true }`. Filled for the example objects only (the Jacuzzi cabinet, the drain valve, the old control room's annunciator); checked by a test that every template resolves to an existing node in the example rooms.
- **Object ports:** from the room layout's port table where one exists (`PORTS` in the museum layouts, `RIG_PORTS`, the CO₂ fittings' `*_PORTS`) or the binding's `ports` map; node ports from section 2.
- **Offered, not made:** an optional `model?: string` on each of 127's named parts and an optional `reads?: string[]` on 131's `Reading` (section 4.5), proposed on the mailbox to their owners; when they land, `PART_BINDINGS` entries they cover are read from them and the table entry is deleted, a test asserting the two agree in the meantime.
- **Annunciator windows:** 127 records an annunciator's named parts (its buttons and horn), not its windows, which the assembly (`control-panels.ts`) draws as one group, so `PART_BINDINGS` has no window label to bind. The reverse audit takes an annunciator's windows instead from the alarm list it is built from (`ANNUNCIATOR_ALARMS` for the old control room's board and the bridge's copies; `LOCATION_ANNUNCIATORS` for a location board), each window → `<room>/alarm:<id>`, `via` that constant, in a small adapter in `part-bindings.ts`. Tested: the old control room's annunciator row lists a `mains-fail` window linking to `control_room/alarm:mains-fail`, and that node's page lists the board back.
- **Repeated labels:** 127's scan keeps a target's part labels unique, so a label that names several parts (a board's twelve identical lamps) cannot say which is which. 127's `TargetRecord.parts` is a set of labels, so from current data the reverse audit can show bindings per label, never per part, and cannot count a label's parts. A binding with `each: true` says every part of that label binds the same node, and is shown once against the label ("lamp: every one → …"); a label without `each` whose parts would bind different nodes is shown as "node: unknown (per part)". Per-part bindings and counts wait for the offered per-part `model` field. `part-bindings.test.ts` asserts this limit: a repeated label yields one row, never a count.
- **Unknown, not flagged:** a part with no binding, from either source, shows "node: unknown"; ports with no table on either side show "ports: unknown". Only declared data raises flags: two nodes at the object's own level (`model` plus a declared own-level binding that disagree), a declared part binding whose node does not exist, or a declared port mapping naming a port the node lacks.

### 4.7 Is anything wrong with it

Flags, each computed from the sections above. Each flag is `yes`, `no` or `unknown`: where its inputs are not yet described (131 covers only the Jacuzzi room and the control room's mimics; adapters and `Reading.reads` are partial), the flag is `unknown`, never a finding:

- `invisible` — simulated (has state) and nothing in the world shows it (no bound object, reading or lamp); `unknown` unless every room it could be shown in (its home room, both control rooms, and any room with a board copy of its home room's mimic) has full coverage (2b).
- `uncontrollable` — its kind is workable (a valve, isolator, switch, starter: `operator` or `Control` exists for its kind elsewhere) and no control targets this one.
- `no-effect` — no downstream edge (a sink kind such as a gully, drain or annunciator excepted).
- `no-source` — no upstream edge (a supply kind such as `incoming-supply`, `water-service` excepted).
- `alarm-not-both` — an alarm it raises does not reach both the old control room and the bridge (the memory rule).
- `missing-tag` / `duplicate-tag` — no derived tag where its kind should have one; or 127's `duplicate-tag` finding.
- `no-state` — no adapter found its state (section 4.3).

## 10. Risks

- **Topology read as causation.** Kept apart by edge kinds and probed drivers (section 2); the impact search must not walk `connects` edges as if they were effects.
- **Incomplete data read as findings.** Flags are `unknown` where descriptors, adapters or scene marks are missing.
- **Two graphs disagree.** Mitigated by the equality test with 129 and by routing 134 through the module.
- **Hand tables drifting** (`ALARM_SOURCES`, drivers, joins). Mitigated by probe tests from fresh worlds; each entry names its evidence (`via`).
- **State outside blocks.** Most state is typed slices, not `Block`s, so section 4.3 depends on adapters; a node without one shows `no-state` rather than a guess.
- **Cost.** Expanding every room's network and the Olympic plumbing is heavy; build per room on demand and cache.
- **Shared files.** `catalogue-panel.ts`, `bench.ts`, `room-audit-page.ts`, `item-audit-page.ts` are claimed by others often; claim on the mailbox first.
- **Layering.** `src/game` cannot import gallery logic (section 5).
