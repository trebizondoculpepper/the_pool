# 134 — Let browser chatbots understand the running plant

The owner, 2026-11-02: while playing in Chrome with a browser-side Claude, Gemini or ChatGPT assistant, ask why an alarm is on, why a backwash is inhibited or why a machine is not working, and get an answer grounded in the current state of the **whole engineering plant**. The assistant must be able to see which pumps are running or tripped, which valves are open or closed, how those components connect and what alarms and events say, including equipment outside the room on screen. The diagnostic metadata should not cover the 3D scene or become another in-game control screen. [Research and proposal](../research/browser-chatbot-context.md).

## First delivery

Create a pure, read-only, versioned projection of the live engineering world. It must enumerate pumps and valves across plant rooms by stable ref, room, maker/kind and model connection, and report their actual and commanded states. For a pump, include mode, running/tripped state, power and isolator availability and flow where modelled. For a valve, include actual open/shut/moving state, command, normal position and the line it connects. Include tank levels, relevant readings, active alarms and recent events. Do not equate an unmodelled value with OFF or SHUT. The API must support small indexed queries by room, system and ref, rather than only one current-room summary or a giant raw world dump.

On that shared projection, begin diagnosis with the Olympic Wash-O-Tron: for each filter's CYCLE NOW, report whether it can start; if it cannot, name the exact interlock and show the readings and thresholds behind it. Explain a first named set of related alarms. Include the world time, current room, focus ref, connected equipment and look links. Reuse `cycleRefusal`, `washSensingOfWorld`, existing alarm predicates, event log, enhanced networks, object refs and control descriptors. Mark causes not yet modelled as unknown, and publish a coverage report for machines, valves and alarms without a reader or cause rule.

Expose a concise facility summary and system index as semantic DOM text outside the canvas, visually hidden but available in the accessibility tree. Offer read-only page methods to list and inspect pumps, valves, connections and alarms on demand, and a readable/copyable diagnostic page with links through those same records for assistants that cannot call JavaScript. Update the summary only when its derived content changes, at most once a second. Do not add it to the saved `World`, and do not expose mutable state or action dispatch through the chatbot surface.

## Proof

Use fixed world states for a running, stopped and tripped pump; open, closed and moving valves; an allowed wash, low flow, pit capacity, pit inhibit, lockout and an active alarm. Query the same pump or valve by tag and from a connected system, including when the player is elsewhere. The text, structured queries and readable report must agree with the model and with each other. Check that a world step updates them, that an index reports missing model coverage, that no changing snapshot causes unnecessary DOM churn, that an assistant cannot mistake old event text for current state, and that the hidden region does not create repeated screen-reader announcements.

Manually test Claude in Chrome, Gemini in Chrome and the ChatGPT Chrome extension with the same saved state and questions about a remote pump, a shut valve, a blocked wash and an alarm; record what each can actually read and whether it answers with the right equipment, connected line and measurements. The readable/copyable report is the compatibility path where hidden DOM or page methods are ignored. Treat WebMCP as a later experimental adapter only if a tested assistant supports it.

## Boundaries and coordination

Publish the whole queryable engineering plant, including machinery outside the player's room, but not the raw save, spoiler state or writable controls. Escape event text and keep content factual, without instructions addressed to a chatbot. Decide with the owner whether the context is on by default and provide an off switch. The first plant-state inventory and PL2 cause rules can start independently of mission 127; broad ref and per-room coverage should follow 127, 129 and 131. Claim shared `main.ts`, menu, catalogue and descriptor files before implementation, since mission 127 is using several of them now.
