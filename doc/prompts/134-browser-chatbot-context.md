# 134 — Let browser chatbots understand the running plant

**Implementation in progress, 2026-11-02.** The first slice is in `src/game/diagnostics/plant-context.ts` and `src/browser/plant-context.ts`: a read-only equipment/valve/pump and location-annunciator projection, bounded page queries, a semantic DOM summary, and a searchable report at `#plant-context-report` with a local off switch. The next slice adds measured tank levels, chemical-store totals, boiler controller states, Olympic flowmeters, Wash-O-Tron alarms and raw wash conditions, plus pump and valve links from the room schematics (`src/game/diagnostics/plant-connections.ts`). The report marks equipment without a live reader as unavailable. Headless Chrome confirms the page API, report search, live links and off switch; it has not yet been tested inside the Claude, Gemini or ChatGPT browser assistants. Other alarm families and machinery still need readers.

The owner, 2026-11-02: while playing in Chrome with a browser-side Claude, Gemini or ChatGPT assistant, ask why an alarm is on, why a backwash is inhibited or why a machine is not working, and get an answer grounded in the current state of the **whole engineering plant**. The first mission is to let the assistant read the basic world model: which pumps are running or tripped, which valves are open or closed, how components connect, and what alarms and events say, including equipment outside the room on screen. The diagnostic metadata should not cover the 3D scene or become another in-game control screen. [Research and proposal](../research/browser-chatbot-context.md).

## First delivery

Create a pure, read-only, versioned projection of the live engineering world. It must enumerate pumps and valves across plant rooms by stable ref, room, maker/kind and model connection, and report their actual and commanded states. For a pump, include mode, running/tripped state, power and isolator availability and flow where modelled. For a valve, include actual open/shut/moving state, command, normal position and the line it connects. Include tank levels, relevant readings, active alarms and recent events. Do not equate an unmodelled value with OFF or SHUT. The API must support small indexed queries by room, system and ref, rather than only one current-room summary or a giant raw world dump.

Include world time, current room, focus ref, connected equipment and look links. Reuse the event log, enhanced networks, object refs and control descriptors. Publish a coverage report for machines, valves and alarms without a state reader; mark unknown or unmodelled fields explicitly. The assistant should be able to inspect the facts behind an alarm or a stopped machine, but this mission does not need a separate hand-authored explanation for every fault or interlock.

Expose a concise facility summary and system index as semantic DOM text outside the canvas, visually hidden but available in the accessibility tree. Offer read-only page methods to list and inspect pumps, valves, connections and alarms on demand, and a readable/copyable diagnostic page with links through those same records for assistants that cannot call JavaScript. Update the summary only when its derived content changes, at most once a second. Do not add it to the saved `World`, and do not expose mutable state or action dispatch through the chatbot surface.

## Later iterations

After the basic world-model surface works in real browser assistants, add model-derived cause explanations such as `whyWashBlocked(filter)` and `whyAlarm(id)`, using the controller's own interlock and alarm predicates as evidence. This can be a later iteration of the diagnostic feature.

Adventure-style narration is also deferred. A later iteration could answer “What's going on here?” with the current location, salient nearby objects and conspicuous live signals, with the player's style preference taking precedence. It would need a player-observable scene selector, distinct from the cross-room plant-state query, and could share that selector with parked mission [128](128-text-adventure-mode.md). Do not build `getSceneContext()`, sense or salience rules, narration prompts, or a default narrator mode in this first mission.

## Proof

Use fixed world states for a running, stopped and tripped pump; open, closed and moving valves; low flow, pit capacity, pit inhibit, lockout and an active alarm. Query the same pump or valve by tag and from a connected system, including when the player is elsewhere. The text, structured queries and readable report must agree with the model and with each other. Check that a world step updates them, that an index reports missing model coverage, that no changing snapshot causes unnecessary DOM churn, that an assistant cannot mistake old event text for current state, and that the hidden region does not create repeated screen-reader announcements.

Manually test Claude in Chrome, Gemini in Chrome and the ChatGPT Chrome extension with the same saved state and questions about a remote pump, a shut valve, a blocked wash and an alarm; record what each can actually read and whether it answers with the right equipment, connected line and measurements. The readable/copyable report is the compatibility path where hidden DOM or page methods are ignored. Treat WebMCP as a later experimental adapter only if a tested assistant supports it.

## Boundaries and coordination

Publish the whole queryable engineering plant, including machinery outside the player's room, but not the raw save, spoiler state or writable controls. Escape event text and keep content factual, without instructions addressed to a chatbot. Decide with the owner whether the context is on by default and provide an off switch. The first plant-state inventory can start independently of mission 127; broad ref and per-room coverage should follow 127, 129 and 131. Claim shared `main.ts`, menu, catalogue and descriptor files before implementation, since mission 127 is using several of them now.
