# 167: Data-first, machine-readable audits

The owner, 2026-11-04: make the system's metadata pages easy for agents and people to audit, and move as much of the audit work as possible into the software. This mission supplies mission 158's registry census with fast, structured evidence. Brief only: the owner will give it to another agent to implement. Read `AGENTS.md`, missions 125–127, 129–130, 145, 158 and 166, and `doc/agent-tooling.md` before implementation.

## Why

The present Room audit builds a 3D room in an iframe to discover its contents, and the unfinished 158 census script also invokes that scanner. That is useful for checking the actual scene but too costly and cumbersome as the ordinary way to review every kind and room. The catalogue (`kindCatalogue`, `lookCatalogue`, `placedRoomItems`), descriptors (`objectDescriptors`) and 158's kind affordance resolver already provide structured data without constructing a scene. The owner wants the existing web audit pages to be the review surface, with JSON or YAML for machine readers instead of requiring them to parse HTML.

A 2026-11-04 data-only probe of `engineers_office` produced six catalogue copies in 1.22 s including Vite module startup, with no browser or scene build: one desk, two cupboards, the Hyperplasc simulator, a supply switch-fuse and a noticeboard. Five have registered kinds; the noticeboard's generic `sign` kind is not in `EQUIPMENT_KINDS`. `objectDescriptors('engineers_office')` returns none. The room's existing source and tests also describe eleven software boxes that are not separate catalogue copies. Thus the fast result is useful but incomplete: absent metadata must never be presented as proof that the room has no other behaving objects.

## Outcome

An agent can fetch a stable JSON document for one room or one kind, read its facts, evidence, gaps and suggested next actions, and link directly to the corresponding web audit. The room and item audit pages show the same data and the same coverage status before any optional scene scan. The owner can review one room at a time, with software-generated proposals clearly separated from recorded owner rulings.

## Data contract

- JSON is the canonical machine format; do not add a YAML dependency merely to offer a second serialization. Provide direct, predictable `.json` URLs for an index, each room and each kind, in both the Vite dev server and the static GitHub Pages build. The response must be actual JSON with the appropriate content type, not an HTML page containing JSON. Keep links relative (`base: './'`). A build may generate untracked JSON assets; do not make a build dirty the tracked tree.
- Use one pure, typed audit model and serializer for the JSON exports and the HTML pages. Include `schemaVersion`, subject ID, stable object refs, registered kind, current resolved affordances, placements, relevant descriptors, source/provenance, findings and summary counts. Order records deterministically. A build or source revision may be included separately; volatile timestamps must not make identical source data appear different.
- Every claim has an evidence state: `declared` (registry, catalogue or descriptor), `observed` (an optional scene scan), `proposed` (software inference), or `approved` (an explicit owner ruling). Each finding has a stable ID, severity, affected room/kind/ref, evidence and source, a suggested next action, and links to the existing item/room/object audit where available. Never present a proposal as an approval.
- Coverage is explicit per subject and per relevant capability. Distinguish `none` (checked and absent), `unknown` (not represented by available data), and `partial` (some evidence but known gaps). A missing descriptor or a zero-copy catalogue row is not proof of no controls, seats or portable items. A room is `signed-off` only when the owner's decision is recorded and its unresolved findings are cleared; the generator must not infer sign-off from an empty list.
- The index lists every active room and registered kind, its coverage and sign-off state, unresolved count and JSON/HTML links. Honour mission 166's retired flags when they exist: show excluded retired subjects and counts apart, without treating deprecated kinds as retired.

## Sources and collection

1. Start with the existing data sources: `src/game/plant/equipment-kinds.ts`, `src/toolkit/gallery/logic/{kind-catalogue,look-catalogue,room-usage}.ts`, `src/game/descriptors/registry.ts` and existing room definitions. Reuse the pages at `bench.html?bench=room-audit&room=<id>`, `bench.html?bench=item-audit&kind=<kind>` and the `?dev` catalogue; do not create a separate report as the owner's sign-off surface.
2. Add a small, typed, scene-free audit manifest beside a room's data or builder only for facts that cannot yet be expressed by those sources. It names the room, owning assembly or kind, stable refs, behaviour observed in source code, and a source pointer. This is a transitional record of gaps, not a second hand-maintained catalogue of everything. Cross-join it automatically with catalogue and descriptors, and flag unmatched or contradictory records.
3. The ordinary JSON export and initial web view must not construct a Three.js scene, canvas, renderer, world simulation or off-screen iframe. Existing visual and scene audit features stay available as an explicit **verify this room** action. Verification runs one selected room, compares observed marks with the data report, adds discrepancies with provenance, and disposes of the room; it must not automatically scan all rooms or run per object.
4. Put the census on the existing pages: the Room audit gets a data-first Registry census section with grouped unresolved owners and proposals; the Item audit shows its kind affordances, evidence and placements. The `?dev` Rooms tab shows not started, proposed or signed off where that decision is recorded. The web pages link to and can download the same JSON. Keep controls and input in the shared controls scheme.

## First room and acceptance

- Use `engineers_office` as the small, reviewable fixture. Its data-only room JSON contains the six known catalogue copies and their correct registry/coverage states. The eleven software boxes described by the room's source and tests appear as named, unresolved or manifest-backed evidence, rather than disappearing or being declared decorative. The page can be read without a room build; its optional verification is a separate action.
- Provide at least one kind JSON example linked from the room, and an index entry for that room. Check the direct JSON URLs on the dev server and from a built static site, including MIME type and relative links. Record cold and warm generation times for the first room; the data path should be comparable to the 1.22 s probe rather than the cost of rendering a room. Timing is reported, not a flaky CI threshold.
- Test the pure joins, deterministic output, schema version, coverage rules, absent descriptors, an unmatched manifest entry, and the distinction between proposal and approval. Verify that the normal export path never calls the scene builder; test the explicit one-room verification path separately. Update `doc/agent-tooling.md` with the JSON URLs, field meanings, coverage states, and verification action.
- Do not turn this into a whole-building playthrough or silently sign off mission 158. Present the first room's report for the owner's ruling; subsequent rooms can be reviewed one at a time. The stage-1 affordance metadata from 158 remains usable by mission 159 independently.
