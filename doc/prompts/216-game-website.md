# 216: a landing page for The Pool Simulation

The owner, 2026-11-05. Build a short public introduction at the root of the existing GitHub Pages site and move the existing web game under `game/`. When the custom domain is connected later, these become `https://thepoolsimulation.xyz/` and `https://thepoolsimulation.xyz/game/`. DNS and the GitHub Pages custom-domain setting are a separate mission, [217](217-custom-domain-dns.md). This website mission is separate from the phone and fault-scenario work.

## Purpose

A visitor should quickly understand that this is an engineering game about finding and fixing the many things that can go wrong in a complex swimming-pool plant, see what it looks like, and have an obvious invitation to try it. The owner's existing tagline, **“The real backrooms of the pool rooms,”** can lead the page, but the supporting line must make the engineering and fault-finding premise clear without relying on the reference.

## Owner-approved content and look

- A concise headline and short explanation of the pool-engineering and fault-finding idea, with little text overall. Use the game's existing light blue, dark blue and yellow logo motifs.
- State plainly near the invitation to play that the game is **free to play and open source**. Link **Source code** to `https://github.com/trebizondoculpepper/the_pool` and **Questions or issues? Open a GitHub issue** to `https://github.com/trebizondoculpepper/the_pool/issues`. The program's licence is GPL-3.0-or-later; bundled media have their own licences in `CREDITS.md`, so avoid suggesting every asset has the program's licence.
- Explain that this is a working simulation: almost nothing in the plant exists solely as decoration. Its machines have state and controls, and the player can inspect, operate, diagnose and put them right. Phrase this as a broad promise about the game's working machinery, rather than claiming every visible object has an interaction or every machine can already be deliberately broken.
- Show that the simulation is also inspectable outside the 3D game. Near the bottom of the page, offer a quiet behind-the-scenes group with **Dev** (`game/?dev`, the room catalogue), **Simulation** (`game/bench.html?bench=sim-graph`, the model graph), and **Bench** (`game/bench.html`, the broader index of rooms, objects, brands and simulation nodes). This is the owner's “backrooms behind the backrooms” idea: optional deeper exploration, subordinate to Play now. Describe these as text and data views into the same model, without promising that every bench control or audit view is a polished player feature.
- Screenshot-derived artwork from the game, a prominent **Play now** action linking to `game/`, and a compact explanation of the activity: explore the plant, diagnose a problem, make the repair. A few captioned images may show the rooms and working instruments.
- **Play now** should launch the game with fullscreen as the intended presentation. Request browser fullscreen from the player's launch click where the chosen routing allows it; if navigating to `/game/` or browser support prevents that, show a clear **Enter fullscreen** control in the game rather than implying fullscreen succeeded. The game remains playable in the browser window when fullscreen is unavailable, with a way to leave fullscreen.
- Offer compact graphics launch choices for slower computers: **Low**, **Medium**, and **High**, using the existing `game/?graphics=low|medium|high` launch parameters so the preset is applied before the first rendered frame. Plain **Play now** omits that parameter, letting the game retain a returning player's saved choice or use its default for a new visitor. A visitor can choose a preset before launch, and the game's Settings can still change quality later.
- Use time spent on the static landing page to warm the browser cache for a small set of assets needed at game startup: the game document, its entry bundle and the title screen's essential art or audio where useful. Start those future-navigation requests at low priority after the landing page's own content is visible, and increase priority when the visitor approaches Play now. Derive any fingerprinted bundle URLs from the build rather than hard-coding them. Avoid fetching room-specific 3D assets, the whole game, or large media speculatively; respect constrained connections and confirm with a cold-cache versus warmed-cache launch measurement that this helps without slowing the landing page.
- A simple email-updates field using Mailchimp's hosted or embedded form, with confirmation and a short explanation of what subscribers will receive. The owner will set up the Mailchimp account; do not build a mailing-list backend for this mission. Keep the form integration replaceable if the list later moves elsewhere.
- A restrained footer with the real source, licence and GitHub issues links; add contact or social links only where real destinations exist. Do not invent a press kit, FAQ answers, social accounts or email address.

## Delivery

Keep the game's relative asset paths working when it moves from the site's root to `game/`; preserve direct game and room links and the local development workflow. Keep navigation relative to the published site root: `game/` from the landing page works both at today's `https://trebizondoculpepper.github.io/the_pool/` project URL and at the later custom-domain root, where it resolves to `/game/`. The build and GitHub Pages artifact must publish both pages without requiring DNS changes. Do not set the custom domain, edit Porkbun DNS, or redirect the public root to the game in this mission; [217](217-custom-domain-dns.md) owns the domain cutover.

## Acceptance

At the site root, a desktop or phone visitor sees the pitch, game-derived artwork, matching colour palette, a clear `/game/` launch, graphics quality choices and the simple updates form once the owner supplies Mailchimp details. The lower part of the page has quiet Dev, Simulation and Bench links. A launch with Low, Medium or High applies that preset before the first game frame. Fullscreen is attempted from a player gesture where supported, with a visible game-side control and windowed fallback where it is not. `/game/` loads the existing game with working assets and direct links; the three behind-the-scenes links open their existing views. A warmed visit can reuse fetched startup assets and measurably launches faster than a cold visit, while the landing page remains quick on constrained connections. The page has readable text and sensible image alternatives, and the form does not imply that it is live before its real Mailchimp destination is configured.
