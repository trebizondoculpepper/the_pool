# 141 — Browser access to the live simulation graph

**Revised proposal after ChatGPT feedback, 2026-11-02. No implementation authorised yet.** The owner has confirmed that ChatGPT can read the browser diagnostics introduced by [134](134-browser-chatbot-context.md) and [139](139-browser-plant-process-state.md). It can inspect water chemistry, equipment state, alarms, CO₂ demand and delivery, and simulation-time trends. It cannot yet discover a component's full connections or walk from a sensor through a controller and actuator to a physical process. [140](140-plant-wide-ai-observability.md) covers broader live facts and causal diagnosis; 141 supplies graph evidence for those explanations through the browser access ChatGPT actually has.

## Existing capabilities

- The simulation is built from port-addressed blocks and room enhanced networks; electrical feeders and installed equipment provide further relationships (`doc/plant-model.md`, `src/game/sim/`, `src/game/plant/`). A connection needs its actual source, port, medium and direction to explain anything.
- [138](138-simulation-graph-audit.md) has delivered a pure, cached `simGraph()` in `src/toolkit/gallery/logic/sim-graph/`. Its node IDs look like `plant_pool_02/node:pumps`. Nodes, typed edges, ports, media, provenance and collapsed connector runs come from schematics, parts, cross-room joins, alarms and leaves. `resolveRef` maps a room object to a node; `neighbours(graph, id, 'up'|'down', filter)` returns direct neighbours. Control, reading and board-copy relations are separate records. The `bench=sim-node` page and Simulation catalogue expose these for developers.
- [134](134-browser-chatbot-context.md) exposes `getConnections(ref)` through `window.__poolDiagnostics`, but its current `plantConnectionsFor` reads touching room-schematic links for catalogued equipment. It returns names, ports, valve positions and endpoint refs; it is not a complete cross-domain or multi-hop simulation-graph traversal. Its full report adds these links only for a small search result. The normal page's semantic index has equipment and process facts but no graph explorer.
- The plant report from 134 and 139 already has a read-only, accessible DOM surface and a local off switch. The same process snapshot and world time can annotate graph results without copying mutable simulation state.

## Why ChatGPT cannot traverse it today

ChatGPT's present browser tool can only **list already open tabs and read one tab's extracted page content**. It cannot open a URL, navigate the tab, click, type or run JavaScript. It can read ordinary DOM text and visible link URLs; after a human changes the tab, it can read the updated page. Advertising `getConnections()` or rendering followable node links therefore does not give this agent autonomous traversal. The useful 138 audit is a development route on `bench.html`, describes a fresh world rather than the running saved world, and is not integrated into the player-facing diagnostic report. The current ordinary report gives neither a facility graph inventory nor a bounded, self-contained graph investigation. Also, topology is not automatically causation: `connects` records a routed link and its orientation, while actual flow, controller effect or downstream impact must be checked against live state and model rules.

## Options and recommendation

| Option                                                                                         | Works with ChatGPT's current tab reader?             | Limit                                                                                                                                               |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deep-linked node pages and indexed JavaScript queries                                          | No autonomous traversal                              | Useful for humans and richer agents, but ChatGPT cannot invoke or navigate them.                                                                    |
| Entire graph in one page                                                                       | Only if the complete useful text survives extraction | Large, repetitive, expensive to refresh and likely to crowd out current process evidence; measure graph and extraction sizes before considering it. |
| Compact graph inventory plus automatically selected investigation bundles in the existing page | Yes, within a measured extraction budget             | Can investigate faults selected by alarms, events, discrepancies and current room; a silent fault outside those roots may remain uncovered.         |
| User-selected graph focus or copied report                                                     | Yes after a human action                             | Helpful fallback, but does not meet autonomous fault discovery.                                                                                     |

**Recommend the third option.** Extend the ordinary, already readable plant report with a compact **graph atlas** and a bounded set of **live investigation bundles**, rendered as ordinary text in the same tab without input. The atlas gives stable tags and node IDs, rooms/systems, roles, a short list of immediate typed neighbours, and coverage/truncation counts. Organise it by system and put a concise facility index before detailed text. Measure the actual graph size, rendered text size and what ChatGPT receives. If the whole atlas does not fit, keep a compact facility-to-system-to-node index and state exactly which nodes and links were omitted; do not claim arbitrary discovery.

Select bundle roots automatically from current active alarms, changed/tripped equipment, command-versus-actual discrepancies, abnormal process measurements, recent interventions and significant trends, with deterministic priority and per-domain quotas so one widespread fault cannot crowd out all others. Include the direct neighbours, a small number of model-validated upstream supply/control paths and downstream consumers, current states, measurements and recent events. The user need not select a ref or navigate. A quiet system may also get a small baseline bundle, such as the Pool 02 Aqualis control and dosing path, to test discovery when no alarm exists. Clearly state the selection reason, what was omitted by budget, and whether an unreported system has not been checked.

Compute the atlas and bundles from 138's graph plus 134/139's live readers; no parallel simulation state. Show distinct sections for **discovery**, **local connectivity**, **path evidence**, **potential dependencies** and **causal evidence**. A bundle is a precomputed answer substrate, not a text diagnosis: ChatGPT can reason from the edges and facts. Use one stable canonical node ID and explicit ref mappings. Keep the existing AI-context off switch and read-only boundary. The DOM view is the primary delivery for this agent. Deep links and `window.__poolDiagnostics` graph queries are optional secondary adapters for humans and more capable tools, not acceptance evidence for ChatGPT.

This cannot guarantee arbitrary traversal through an unbounded graph. If the fault is neither in the extracted atlas nor in an automatically selected bundle, this browser tool has no way to request missing nodes. The proposal's honest success target is broad, measured fault discovery and diagnosis within the report's coverage and extraction budget. The owner's “break anything” ambition requires either full useful graph coverage in the readable tab or a browser tool with navigation/query capability; record the gap rather than hiding it.

## Traversal and live evidence

The node view should show its ID, tag, kind, room, role, parent/children, model address if safe, live state and freshness, measurements with units, commands versus actual response, alarms and recent events. List each edge with source/target node and port, medium, edge kind (`connects`, `contains`, `feeds`, `raises`), direction, source/provenance and any collapsed connector run. State explicitly whether the relation is a physical link, signal/control relation, containment, alarm source or display copy. A display copy is not another actuator, and an alarm relation is not a fluid path. Mark unresolved joins.

For each bundle, start with direct neighbours; compute a few bounded, relevant paths and impacts in advance. Implement path finding and impact search as a separate bounded walk over explicit allowed edge kinds, with visited-node and cycle handling, a returned path for each reached endpoint, and a truncation/limit marker. The 138 `ImpactSearch` is only a typed hook today. A general walk over every edge would give misleading answers: require a traversal purpose (water route, electrical supply, control command, sensor signal, heat delivery or alarm provenance) and treat passive connector runs as compact evidence rather than thousands of rows. A path is a **possible dependency** until live state and a model rule support an actual effect. Show where the graph has no edge or where the edge is only schematic/unverified.

Join graph nodes to current equipment, process and alarm facts by explicit IDs or validated bindings. Do not infer a match solely from a similar name. On a path, annotate a breaker or isolator's actual state, a controller's request, a pump's running and delivered flow, a valve's actual position, and receiving water measurements where modelled. A closed valve, tripped supply or inactive controller may make a physically connected path inactive at this simulation time; state that distinction. Keep observations, model-backed consequences and untested hypotheses separately labelled.

Classify every reported relationship on two axes. **Structural source:** executing model connection with a validated runtime binding, schematic connection whose runtime effect is unverified, or explicit diagnostic inference; cite the underlying source and mark an absent binding. **Live condition:** actual flow or signal observed, potential path available, path inactive due to a measured/known constraint, or unknown because the model lacks the relevant reading. The direction drawn in a schematic is not a measured direction of current flow. A controller-to-actuator relation is a command path; whether the actuator moved or changed water is separate evidence. Never promote a development-audit edge to an executing causal link solely because it appears in `simGraph()`.

## Dr Aqualis example to prove

The example is a **target investigation bundle**, not an assertion that every edge already exists in 138. The atlas identifies the Pool 02 Dr Aqualis controller by canonical node ID and tag; a disturbance, dosing discrepancy or baseline selection puts its relevant subgraph into the readable page automatically. That bundle names incoming sample-flow and probe signals, the sampling point and live sample-flow/chemistry readings, or marks a missing graph relation. It names outgoing dosing-channel commands to the specific pump, CO₂ valve or other actuator represented by the model; shows requested output versus actual delivery and inhibit/fault state; then gives the chemical/CO₂ supply and injection path into the return line, toward the main pool and back through the balance tank. Each step has source and target ports, medium, current state and evidence source. The shared CO₂ isolation/supply path to Pool 01 and Pool 02 is visible if validated. If a pump, valve, injection junction or water-body relation is absent from the graph, the bundle says so and the mission records a graph-coverage task rather than inventing a direct controller-to-water edge. ChatGPT reads this self-contained bundle without navigation.

A sample browser answer after an isolated CO₂ supply fault would read: “The Pool 02 controller requests CO₂; the model connects that channel to its dosing valve and shared supply path; the shared isolation is shut; measured line pressure and actual delivered rate are low/zero; Pool 02 pH has not yet fallen over the observed interval.” Every clause must link to a current fact, model edge or timestamped trend. The example must be tested against actual world state; values and path refs are not hard-coded into prose.

## Practicality and scope

Build the graph once as 138 does, and query indexed node/edge maps rather than scanning and serialising it on every page refresh. Measure node/edge counts, per-domain coverage, atlas length, bundle size and the actual extracted page text, including where it truncates. Give each bundle explicit node, edge, depth and text budgets and a visible omission count. Prioritise the current fault evidence before broad inventory and stable baseline content; refresh live annotations only when displayed state changes, at most once a second, using simulation timestamps, while topology stays cached. Avoid repeated screen-reader announcements. The full graph can still have developer deep links, but the acceptance test reads only the already open game tab.

First inventory graph coverage by domain, including nodes missing live facts, non-resolving equipment refs, missing control/chemical paths and cross-room joins; quantify graph and browser extraction budgets. Then specify the atlas, bundle selection and fact/edge contracts, integrate the live facts, add bounded path/impact computation, and validate accessible DOM extraction. Do not alter physical simulation merely to complete the graph. Reuse 138's graph, 134/139's diagnostic readers and report, control descriptors and the event log. Likely shared touch points for a future implementation are `src/toolkit/gallery/logic/sim-graph/`, `src/game/diagnostics/`, `src/browser/plant-context.ts`, `src/browser/plant-context.css` and `doc/agent-tooling.md`; claim them with other agents before implementation. No save migration should be needed for a pure read-only projection, but reserve `WORLD_VERSION` if a later plan changes saved state.

## Success test for the future implementation

With the player in another room and without telling ChatGPT the intervention, introduce a Pool 02 dosing fault and an independent electrical or heating fault. **Using only list-tabs and read-tab on the already open game page**, ChatGPT discovers the affected nodes in the atlas or selected bundles, follows the reported typed paths in the text, cites the upstream constraint and downstream affected equipment, compares commanded and actual live state, and distinguishes a possible path from a proven current effect. It reports missing edges, live readers, omitted sections and incomplete coverage accurately. Test at least one fault with no alarm or event, and measure whether the selected bundles still include it; if not, document the limitation. The owner and ChatGPT review this revised proposal before any code work begins.
