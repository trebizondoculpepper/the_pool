# 225: Composable room traits — research report

Short title: what special behaviour is bound to rooms today, and what reusable room traits would let any room opt into it.

Issue [#96](https://github.com/trebizondoculpepper/the_pool/issues/96): research and proposal only. No room-trait runtime and no room migrations were implemented; this report decides the candidate trait set for a later implementation issue. Draft brief: [doc/prompts/225-room-traits-research.md](../prompts/225-room-traits-research.md). This is the deliverable linked from the issue.

## Summary

The game's special room behaviours fall into five homes, and only a small set genuinely wants a new "room trait" system. Most per-room behaviour is already shared _below_ the room (equipment's own simulations, the world model, the control scheme) or is ordinary content. The behaviours that are selected by a room's identity today — and would be better as reusable, composable room traits — are:

1. **dev0's action log** (parts' events shown in a DOM overlay) — a `dev-` trait over the shared `onEvent` mechanism.
2. **The museum's visitor games** (Hall 4 challenge, Hall 9 faults, Hall 8 narration, Hall 5 skimmer) — each is a room-scenario _engine_ with a reset-on-entry lifecycle; the shared `LiveExhibit`/`ExhibitHooks` machinery already carries the lifecycle, so the trait surface is mainly "declare which engine, with what configuration".
3. **Room-timed, room-simulation-timed events** (dev71's phone text trial — built, issue #79/215; Hall 1's session clock; dev5's 10 s restock; Hall 4's 60 s clue) — a small set of _timing_ capabilities (room-sim clock, pausable timer, on-entry reset) that would compose.
4. **Per-room presentation** (dev31's effects console, dev54's PS1 judder, dev60's sky changer, the corridor's zone culling) — mostly already parameterised presenters or world systems; the trait surface is "which components to install".

The genuine one-off phone trial is dev71's (issue #79 / 215), already marked and built; the trait surface it demonstrates is `room-sim-clock` + `timed-delivery` for future rooms.

## Critical findings that change the brief

1. **dev71 exists, built exactly as the owner described.** This research's first survey was run on a branch cut before dev71's merge (issue #79 / brief 215); the room is on `main` now. dev71 is a blank phone-interaction dev room (`dev-room-links.ts:83, 199, 532, 671` — "DEV71 · PHONE INTERACTION") whose room-wide script `createRoomScript()` uses a shared pure helper, `createPhoneMessageTrial` (`logic/phone-message-trial.ts`): elapsed room-sim time, thresholds at 20 s and 120 s, one-shot delivery into the shared `phoneInbox.receive`; leaving/reset cancels and revisiting replays. It is the **best existing model for this research**: the timed two-message delivery is a _parameterised capability_ (`[20, 120]` thresholds + a deliver callback) that composes with the shared inbox — but it is not yet composed as a room trait; it is installed per-room via `plant-room.ts`'s dev-room table and `main.ts:1239`. Extract `room-sim-clock` + `timed-delivery` from it.
2. **The `One-off (the owner, 2026-11-05):` comments exist for the phone trial** (both `phone-message-trial.ts:1` and the room script) — the owner approved the scripted behaviour as an exception to the shared-system rule and it was marked as such. The broader label sweep is still pending for the skimmer's magical sign etc., but the pattern is now in the tree; this research's earlier "zero labels" claim was stale (pre-merge survey).
3. **The existing `room-traits.ts` is an object-trait projector, not a room-trait registry.** `src/toolkit/gallery/views/room-traits.ts` maps _object_ kinds' traits (holdable, supportable, racks, bins, solids) into rooms through `useRoomTraits`/`RoomTraits`. A proposed room-level trait system must not reuse that name, which would confuse object traits with room traits. The report proposes `room-features`/`RoomFeature` below, and recommends renaming the projector's export (e.g. `objectTraits`) only in the later implementation issue, not here.

## Method and scope

- Surveyed all development rooms from `dev-room-links.ts` (`DEV_ROOMS`, `ROOMS`, `DEV_ROOM_NAMES`, per-room comments), the museum halls (`museum-plan.ts`, `museum-hall-model.ts`), the pool halls (`pool-hall-room.ts`), and the room factories/starters in `src/rendering/`, plus `main.ts`'s room router.
- Used the project tools first where the AGENTS rules demand (look links, `?dev` catalogue data, descriptors, audits); no cameras were placed.
- One source-backed row per special behaviour (below); ordinary scene content and equipment placement recorded separately and _not_ treated as traits.
- Boundaries kept: equipment behaviour stays with object kinds; world-wide player behaviour stays with shared systems (controls, world, save); room-specific clicks/aims follow #8's one-click-handler inventory (`doc/plans/161-one-click-handler.md`) and belong on the shared resolver as object registrations, unless the behaviour is genuinely room-wide (then it is a room feature candidate).

## Classification framework

Each behaviour → one home:

| Home                                       | What goes there                                                     | Example                                                             |
| ------------------------------------------ | ------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **Object-kind/model behaviour**            | what a kind of equipment does (its parts, world binds, simulations) | valve rig, pumps, spa panel, fibre-optic wall                       |
| **Global system**                          | world-wide player behaviour shared by every room                    | phone, controls, water, save, lights                                |
| **Room feature (the proposed new system)** | behaviours a room declares to opt into, parameterised               | action log, room-sim timer, scenario engine, presentation component |
| **Configuration of a shared trait**        | same capability, different parameters                               | dev39's scenario stores; museum halls' reset-on-entry               |
| **Ordinary content**                       | scene objects, placards, specimens                                  | museum7, dev45/46/47/48/49/50/51/70 bodies, pool hall furnishing    |
| **Justified one-off**                      | truly happens once, with `One-off (the owner, <date>):` recorded    | skimmer's magical sign + suspense reveal (currently unlabelled)     |

Material boundary rules (from #8/#95/#94 and the brief):

- Room-specific clicks and aims → **object registrations on the shared resolver** (#8), including `plant-room-shell-room.ts`'s hand-written `useOf` (#95). Rooms must stop walking `parts.uses`/`machines.useOf` by hand.
- Per-action reach (#94) → a property of the _action_, not the room: the shared aim already has per-reach support; a room feature must not re-add reach rules.
- The existing `room-traits.ts` (object traits projected into rooms) is **not** the room-feature registry; keep the names distinct (see Findings 3).

### Worked decomposition — dev0

- **Event source**: already shared — every part emits `onEvent(event, name)` (parts.ts); dev0 subscribes (`controls-room.ts:487`).
- **Display**: room-local DOM `<ol role=log>` capped at 10 (435-462).
- **Setup/clearing**: element appended at start, removed on dispose.
- **Trait**: `parts-action-log` — subscribe to the room's parts' shared events, render the list. Dev-only, not for ordinary rooms (a broader "audit trail" may later want it in plant rooms; keep `dev-only: true` for now).

### Worked decomposition — dev71 (built, issue #79/215) and its trait shape

- dev71 exists on main: a blank phone-interaction room whose room-wide script (installed via `plant-room.ts`'s dev-room table and `main.ts:1239`) runs the shared pure `createPhoneMessageTrial(deliver)`: elapsed room-sim time, thresholds `[20, 120]` s, one-shot delivery into the shared `phoneInbox.receive(…)`; leaving cancels and revisiting replays via the exhibit-room runner's per-visit reset/step hooks while the room is visible. Marked `One-off (the owner, 2026-11-05):` with the reason.
- **Trait shape to extract** (for any future room, without the one-off): `room-sim-clock` (runs while the room is active, paused with the world) + `timed-delivery` (a list of `{at, deliver}` thresholds, `resetOnRevisit: true`), composing **`dev-mobile-phone-experiment-zero`** (the owner's name) that delivers into the shared phone inbox. dev71 is the proof this works; the trait generalises it.

### Worked example — two traits composed in one room

A future dev room (or the skimmer's hall) declares `scenario-engine` + `parts-action-log`:

```ts
// room makes { features: [...] } or the factory reads a room manifest
features: [
  { feature: 'scenario-engine', engine: 'museum-skimmer', resetOnEntry: true },
  { feature: 'parts-action-log', position: 'top-left', max: 10 },
];
```

The factory installs the engine (reset on entry, update while active via the shared exhibit hook) and the log (subscribes to the same parts' events) — neither feature knows the room's ID; a different hall could enable the log by declaring the feature. The one-click-handler resolver still owns every click.

## Implementation order and risks (for the later issue)

1. **Resolution first**: land #8's room migration and #95, so clicks/aims leave the rooms before any room-feature declares behaviour for them. A room feature must never re-add a click walk.
2. **Add the capability primitives** (`room-sim-clock`, `timed-delivery`, `scenario-engine`, `parts-action-log`, `film-capture`, `dev-input-shortcut`), each pure, tested, behind the factory's manifest, **without** migrating any room yet.
3. **Label the genuine one-offs** (`One-off (the owner, <date>):` under the skimmer's magical sign and suspense reveal; audit any others) so the trait system does not claim "no special cases" while they exist unlabelled.
4. **Migrate rooms in visible batches**, starting with dev0 (log) and a museum hall declaring `scenario-engine`, keeping behavior identical (tests per batch: the hall's reset-on-entry, update-while-active, and save rules).
5. **Add the named composites** (`dev-mobile-phone-experiment-zero` generalises dev71's built trial; `museum-*` engines).

**Risks**: the room router in `main.ts` is a long ID chain — a manifest of features must be a _data_ lookup, not another ID branch; the existing `room-traits.ts` name collision (finding 3). No behaviour changes are made by this research.
