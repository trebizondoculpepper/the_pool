# World model speed investigation — mission 042

Research for the owner, 2026-11-07. This is a measured first pass against `833611a2` on an Apple M5, Node 26.10.0, Vite Plus 1.2.0. The temporary Vitest experiments and CPU profile were not merged. Values below are local samples, not performance budgets or browser frame timings. The 2026-10-24 numbers in the [brief](../prompts/042-world-model-speed-investigation.md) describe an older world and should not be used as today's baseline.

## Recommendation

Resolve repeated static valve lookups once, then measure the whole world again. `installedValveOpen` scans 150 installed valves by tag, while `distributionPaths` repeatedly looks up static model valves during each world step. The isolated experiments show substantial savings with a tag map and precompiled valve references, with unchanged results for the normal state, a changed state and 40 individual valve toggles. These are safe candidates for a small, separately reviewed implementation. The experiment does **not** establish a whole-world speedup.

Keep the existing 16-entry hydraulic solution caches. Do not enlarge the world step or remove the catch-up cap until fault, threshold and event histories are checked for equivalence. A worker may protect rendering from a slow step, but it would not make the calculation cheaper and its message-copy cost needs a browser measurement. A flat typed-array world or WebAssembly kernel has no measured benefit yet and would impose a broad conversion and save-migration cost.

## Baseline and method

The temporary benchmark warmed the world for 100 steps, measured 3,000 more `stepWorld(world, 0.1)` steps, measured one hour through `advance`, and serialized the resulting world. It used `performance.now()` and an inspector CPU profile over 15,000 steps. A five-world proxy stepped five independent new worlds; those worlds do not form one larger connected plant. The experimental tests themselves checked candidate lookup outputs against the current code; their files are removed after reporting.

| Measure                                 |                   Current result | Earlier brief, for context |
| --------------------------------------- | -------------------------------: | -------------------------: |
| One 0.1 s step                          |                          ~162 µs |                     ~25 µs |
| One simulated hour, 36,000 normal steps |                          ~4.61 s |                     ~0.8 s |
| Full serialized world                   | 43,889 bytes, including envelope |                    ~5.5 KB |
| `footbathLineup` alone                  |                    ~1.54 µs/call |   ~11 µs/call, 45% of step |
| `structuredClone(world)`                |                     ~153 µs/call |               Not measured |
| Five independent worlds                 |           ~128 µs per world-step |               Not measured |

The current `identifiedPart` reader has a WeakMap index tied to the immutable identified block, which explains why the old `footbathLineup` hotspot is no longer the main target. The inspector sample instead concentrated in `chemical-valves.ts`, `installedValveOpen`, `stepPlant`, `stepPoolsWater` and `olympicBatteryFlows`. Profile sample counts identify areas to inspect; they are not exact time percentages. The five-world proxy benefits from warm JIT and does not model fivefold graph connectivity, shared supplies or memory pressure, so it cannot predict the eventual 4–5× plant.

The valve microbenchmarks include checksum use of their results to prevent unused-call elimination. The precompiled experiment still constructs an output object, so its result reflects removal of repeated static searches rather than eliminating every allocation. Its ~87× local ratio must not be multiplied by the world's step rate as a promised total gain.

## Remaining validation for full mission closure

Mission 042's original method asks for before/after **whole-world** measurements for every candidate, a faithful 4–5× connected plant, and equality of world results after each experiment. This first pass does not supply those for compiled state or a worker, nor a fault/event equivalence study for catch-up. The report gives a ranked implementation decision now, but the original broad investigation remains incomplete until those experiments are either performed or the owner narrows its acceptance criteria. A future benchmark harness should be kept as a `*.bench.ts` or reporting test only after review; no temporary experiment file belongs in the production test suite.
