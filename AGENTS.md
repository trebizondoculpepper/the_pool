# Pool Plant project guidance

`CLAUDE.md` is a symlink to this file. Read `README.md` and the owner's project brief (`/Users/salimfadhley/Downloads/Pool-Plant-Project-Brief.md`) before implementation.

## Picking up a job

1. Read the mission brief in `doc/prompts/` and its linked plan and `TODO.md` items before editing. For a job without a mission, read the owner's request and the relevant project guidance; settle any material ambiguity with the owner, one question at a time.
2. Tell the other Pool Plant agents through agent-inbox which job you are taking, which files or systems you expect to touch, and any likely overlap. Address the project's agents, not the whole hub. Check their current work and coordinate shared files before changing them.
3. Implement and verify the job. Keep `TODO.md` and `CHANGELOG.md` current, and run the required checks below before committing.
4. Normally work on `main` without a branch. In the shared checkout, stage only your own files and check the staged diff; do not include another agent's uncommitted work. Commit your job, check that `origin/main` has not moved, then push. If it has moved, integrate the new work and rerun affected checks before pushing. A push to `main` deploys the GitHub Pages build; a release happens only when the owner asks.
5. After the push, tell the other Pool Plant agents what finished, give the commit, mention any follow-up, and invite them to pull, review and comment. Respond to findings and correct the work when needed.

While several agents work at once (the owner, 2026-11-01):

- **Claim shared files.** Say on the mailbox which files and systems your job touches. Keep out of another agent's claimed files until it says they are free, and say so when you free your own. Changing a claimed file needs that agent's agreement first.
- **Reserve a `WORLD_VERSION` before taking it.** Agree the next number with the other agents on the mailbox before you bump it or add a `save.ts` migration. Two jobs must never take the same number. Whoever merges second rebases onto the other's migration and keeps its own number.
- **Say what a job waits on.** A brief that depends on another job's result says which parts can start now and which must wait (mission 118's Coordination section is the pattern). The agent whose work it waits on mails when that work has merged.
- **Everyone works in the main checkout, on `main`, with no git worktrees** (the owner, 2026-11-01), so all work shows on the one shared dev server. **Ask the owner's permission before starting a worktree**, for yourself or for any subagent you spawn (no `isolation: "worktree"` without it). The owner typically runs several agents from one checkout and gives them orthogonal jobs; coordinate through agent-inbox (claims, `WORLD_VERSION`, what you're touching, what you've pushed), not by isolating. Because the checkout is shared, stage only your own files or hunks (never `git add -A`, nor a whole `TODO.md` or `CHANGELOG.md` holding others' lines), check the staged diff, then pull with `--rebase` and push. Expect a test run to see other agents' unfinished edits; rerun a failure before blaming it on them.
- **One shared dev server on each machine, open to the LAN** (the owner, 2026-11-01), so the owner can test from an iPad or phone. The game is developed on two Macs, the MacBook Air (`trebizondo`, 192.168.86.22) and the MacBook Pro (192.168.86.87). Each runs one Vite server from its main checkout with `npx vp dev --host 0.0.0.0 --port 5175 --strictPort`, at `http://<its address>:5175/`. Don't start a second server on 5175 or bind it to 127.0.0.1 only. If you must restart it, restart it the same way, and say so on the mailbox. Your own throwaway server, for screenshots, goes on another port and is stopped when you're done.
- **One full test run at a time on each machine.** A full `npm test` takes several minutes and overlapping runs slow each other into timeouts. Say on agent-inbox when you start one and when it finishes ("Starting a full npm test now"), and don't start another while one is announced as running; run your targeted tests meanwhile, with `--maxWorkers=2`. Wait on a run with `kill -0 <pid>`, never with a `pgrep -f` pattern that matches your own command.

## Rules

- Every room is, for now, a blank shell with a title card on one wall. Do not add equipment, pools or scenery until the owner asks.
- The building is one contiguous world in metres (one scene unit is one metre); rooms are rectangles in `src/game/facility-plan.ts` joined by doorways in shared walls. No portals.
- The exception is the pool loop (`src/toolkit/gallery/logic/pool-loop.ts`): the version-one pool halls are blocks joined one after another by short corridors of the corridor kit, round and round for ever, making no three-dimensional sense on purpose. Each corridor leaves a room by its north wall and enters the next by its south (so the walker keeps going forward and usually sees the way out across the room); walking along one hands the walker into the next room's scene, where the same corridor carries on. Each corridor is a short straight (1 m), one piece chosen at random (a left or right turn, or a flight of stairs up or down), and another short straight, so it always meets a room square on.
- The adjacent `/Users/salimfadhley/workspace/encabulator` repository is a source of reusable components. Leave it unchanged. Record every copied file, and any adaptation, in `doc/reuse-inventory.md` before or as it is copied.
- Anything to do with engineering and maintenance is a real, working component, modelled after a real product: it has state, can be driven, and shows what it is doing (gauges read values, switches switch, lamps light, recorders record). No static props for engineering items; only pure set decoration (plants, furniture) may be static.
- One exception: a procedural services ceiling (cable trays, ducts, sprinkler and other pipework overhead, `src/toolkit/components/site-dressing/`) may be used as a static background layer, for depth and an industrial feel in spaces outside the plant and over the development rooms (the owner put one over dev61, pumps). It is set decoration and is not part of the plant model; the owner has since asked for one over every plant room too, high under its roof, as background above the real, connected pipework the plant rooms will hold, which stays the plant model's.
- New pool rooms are coved by default: every junction of an upright wall with another wall or with the deck gets a tiled quarter-round fillet (`src/toolkit/components/architectural/views/room-coves.ts`, 0.25 m), so no corner is sharp.
- Every door from a pool hall to its plant room is the same template (`src/toolkit/components/architectural/parts/plant-door.ts`, placed by a hall's `plantDoor` in `src/toolkit/gallery/logic/pool-halls.ts`): an Ironside FD60 steel doorset, its 926 × 2040 mm leaf in a steel frame all round (sill included), self-closing, opening either way; PLANT ROOM, Authorised Personnel Only and Fire Door Keep Shut signs on the hall side, and a card reader on the wall beside it (seen, not worked). Its sill stands 0.25 m up, above the cove between deck and wall, so the fillet runs on unbroken under the door. Doors between plant rooms are larger, for equipment.
- Corridors follow one template so they join easily: 1.2 m wide, 2.5 m tall, rectangular, with a filleted (coved) junction wherever a wall meets the floor or the ceiling. They are dry rooms. The one exception is the Olympic pool's underwater viewing gallery, which is part of the Olympic pool's model.
- Model new equipment in the development rooms before it goes into the leisure centre, and try any new kind of control or display on dev0's boards first; assemblies built from many of them (mimics, control boards, a cubicle's fascia) are tried in dev39, the control assemblies room (the owner, 2026-10-25).
- Every development room has a number (`dev65`), and may have a name too (`dev65 · Boiler room`, shown on its title card and in `?dev`) (the owner, 2026-11-02). A new dev room takes the next free number in `dev-room-links.ts`. The rooms once known by name alone were numbered on 2026-11-02, keeping their names: dev59 the dev corridor (was `dev_corridor`), dev60 the courtyard (`dev_courtyard`), dev61 pumps (`dev_pumps`), dev62 balance tanks (`dev_balance`), dev63 chemical store (`dev_chemicals`), dev64 dosing (`dev_dosing`), dev65 boiler room (`dev_boiler`), dev66 air handling (`dev_air`), dev67 electrical (`dev_electrical`), dev68 control centre (`dev_control`), dev69 ozone (`dev_ozone`). The old ids still work through `ROOM_ALIASES` in `dev-room-links.ts` (`resolveRoomId`, and the page's address is corrected to the number); use the numbers in new code and docs.
- Control systems lean old (much of the plant around 2000; see the period rule below): many single-purpose instruments (analogue gauges, moving-coil meters, LED and LCD readouts, chart recorders, annunciators, mimic panels, a few CRTs) rather than one screen showing everything. Computers, where there are any, are obsolete or special-purpose. The control room is where problems are diagnosed; putting them right often means going to the room concerned.
- The control room is the old control room by default, the bridge behind the CONTROL ROOM MODE knob (the owner, 2026-10-27, mission 095): the main corridor's control room doors lead to the old control room unless the Dymo-labelled knob beside them (`src/toolkit/gallery/logic/control-room-mode.ts`, the world's `controlRoomMode`) is turned to NEW, when they lead to the bridge, an Easter egg; the bridge's touch screens are its own kind of interface, while the plant rooms keep their single-purpose instruments.
- Everything in the back rooms is made by someone: the pool hall may be generic and nebulous, but every piece of plant, instrument and fitting behind it carries its maker's brand (`brands.ts`). Every mimic, control board and control panel is built by Penfold Controls and carries its discreet mark (`panel-maker-mark.ts`) in its top right corner, or its bottom right where the top right is in use; instruments set into a panel keep their own makers' badges.
- Mimic boards may be duplicated, though a real building would never pay for it: each plant room has the mimics of its own systems (the pump room the water circulation, the boiler room gas and heating), and the control room has one of each, so it gives the central view.
- Some controls are only local (the owner, 2026-10-25): otherwise the player would never need to go anywhere. A control-room board shows everything its plant room's board does and works what its mimic carries (valves' OPEN and SHUT, pumps' START and STOP), but mode selectors (HAND · OFF · AUTO), trip resets and similar stay on the plant room's panel, so putting a fault right means going there.
- The game has one world state (`src/game/world.ts`), which runs whichever room the player is in and is saved in the browser (`src/game/save.ts`, `src/toolkit/save/world-store.ts`): anything that must carry on between rooms or survive a reload lives there, and rooms only show it and act on it. Change its shape by bumping `WORLD_VERSION` and adding a migration. Dev rooms start fresh, except those that demonstrate the world state (dev14 and dev15), which share the `dev` save slot.
- The plant is a model first (`doc/plant-model.md`): blocks within blocks, each showing the world only its ports, addressed by path; machines in the rooms bind to addresses and hold none of the model. Placement follows the schematic and the layout principles there; nothing is decorative, and every pipe is one of the schematic's connections.
- Every museum hall that holds plant (Halls 1, 2, 3, 4, 6, 9) is its own simulation, bound to its own model exactly as the plant rooms are, its machines facing the room; display halls (0, 5, 7, 8) are exempt. See `doc/museum-hall-model.md`; `museum-bindings.test.ts` checks it (the owner, 2026-10-30).
- The enhanced network is the one source of truth (the owner, 2026-10-25): every plant room begins with its schematic, a port graph of its machines with every valve and isolator, each with its function, normal state and tag; its machines are placed where they suit best, but not its valves, which sit in pipes not yet routed; the plumber routes the pipes and sets each of the schematic's valves in its line, as efficiently as its rules allow, and may add valves and isolators its rules imply (a non-return valve on a pump's discharge), each added to the model before anything is drawn; but a correct schematic already has every valve it needs, so the plumber should not have to add anything, and what it adds is a sign the schematic is incomplete. The scene only binds: a machine, valve, isolator or pipe is drawn from a node, fitting or link of the room's enhanced network, and nothing can be put in the visual world that is not already in the model. Tags, names and descriptions are derived from the model algorithmically, never written by hand; tags are hierarchical (PL2-P1-P1: room, pump set, pump). If the network changes, the saved game state may be thrown away. Rooms still drawn by hand are being migrated (`doc/prompts/done/063-component-information-remediation.md`).
- To lay out a plant room, or improve one, read `doc/room-layout-guide.md`: the sizer, regions, placement, blocks and variants, plumber, router and scorer, how to score and search a room, the owner's layout rulings, and the experiment rigs that use them.
- The plant should have a bit of everything: where a real pool might choose one technology, ours may carry several side by side, each real and working, the whole still connected and making sense.
- The game is set in the present day, but its technology deliberately spans the 1980s to the late 2020s (the owner, 2026-10-23): an interesting mix, some things intentionally old, some modern, some intentionally anachronistic, side by side. The point is variety of interaction: buttons, switches, knobs, gauges, meters, lamps, displays and readouts of every kind, each a different way of seeing and working the plant, as diverse as the game can make them. Screens within screens are the least interesting thing to simulate, so no single PC, SCADA or touch screen may take over the instruments; a modern item is welcome where it brings its own kind of interface (a touch-screen controller, a speed gate). Every interface, old or new, must be one the game can simulate.
- All input goes through the one control scheme in `src/toolkit/controls/` (copied from the Encabulator). Rooms do not bind their own keys or gestures.
- Game features not yet designed are stood in for by console commands (the owner, 2026-10-31): `dose` for hand-dosing and the chemical inventory, `test_kit` for the test-kit items. A stand-in works through a real world action and the real model (`src/game/plant/hand-dose.ts`, `test-kit.ts`), logs what it did, and is replaced when the feature is designed; see the console's commands in `src/toolkit/console/logic/commands.ts`.
- Displays redraw only when what they show changes (mission 094; the owner approved it, 2026-10-28): a canvas is drawn and its texture uploaded only when its inputs (its values, page, power, or an animation's phase rounded to what can be seen) differ from those it last drew, compared before any drawing; view state derived from the world is worked out once per world step (`store.read`, or a cache keyed on the world object, as `plantReadingOf` is), not by every display every frame. A display that animates on its own does so at no more than 10 Hz. New displays are run through the component benchmark (`bench.html?bench=components&only=<name>`) and kept within its budget; a component over budget fails the run, unless it is listed with its reason in `KNOWN_OVER_BUDGET` (`src/toolkit/gallery/logic/component-bench.ts`) and flagged in `TODO.md`.
- `src/game/` and every `logic/` folder are pure logic with no DOM or Three.js, tested beside them (`*.test.ts`, importing from `vite-plus/test`).
- Before committing, run `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test` and `npm run build`. CI runs the same and, on a push to `main`, deploys to GitHub Pages (the bleeding edge); only a release reaches itch.io. Vite's `base: './'` keeps asset paths relative; keep links relative too.
- Slow tests, any taking over about 1.5 s or simulating long stretches of world time, go in a `*.slow.test.ts` file beside their fast sibling (shared setup in a small `*.test-support.ts` module beside them). They run locally with `npm test`, which must pass before every commit, and are skipped on GitHub, where `CI` is set (`vite.config.ts`); `npm run test:fast` runs the fast set alone.
- Versions follow semantic versioning (README, "Versions and releases"; mission 104, the owner, 2026-10-28): every push to `main` is the next patch, every release the next minor, a major only when the owner asks. A build never changes the version: it derives the patch from the commits since `package.json`'s version last changed, and writes no tracked file. Never stage `package.json` or `package-lock.json` with ordinary work, only with a dependency change or a release, with one exception: adding or changing an alias in `package.json`'s `scripts` (such as `look:audit`) is ordinary work, staged as that hunk alone, never with a version change (the owner, 2026-11-02); a leftover local version bump from an old build is discarded (`git checkout -- package.json package-lock.json`), not committed. CI fails any commit that changes the version other than a `Release vX.Y.Z`. Add every notable change under Unreleased in `CHANGELOG.md` as you make it, under its Keep a Changelog heading (`### Added`, `### Changed`, `### Fixed`, or `### Removed`, `### Deprecated`, `### Security` where they fit; the owner, 2026-10-31): the release notes on GitHub and itch.io are built from them (`scripts/release-notes.ts`). Keep those headed sections at the end of Unreleased, after any entries written before the rule, which have no heading. Never cut a release without the owner asking; when asked, run `npm run release` (it checks, bundles, commits, tags and pushes).
- Markdown is one paragraph per line, never hard-wrapped.
- Record significant sessions in `diary/`.
- `TODO.md` in the root is the project's one to-do list: every task not yet finished and every item for future delivery goes there, under the section of its kind (gameplay, architectural, lighting, plant features and the rest), ticked off with its date and commit when done.
- Never commit `agent-inbox.toml` (the mailbox identity), its wake-state files or `.claude/settings.json`'s generated wake hooks.
- Ask the owner one question at a time.
